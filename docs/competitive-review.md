# Pixelbolt competitive review

Reviewed 27 September 2026. Scope: agent-driven pixel art, animation, inspection and game export. Evidence is public first-party documentation and repository READMEs, not a hands-on art-quality or performance benchmark. Strengths below are documented capabilities; assessments and priorities are our judgments. Lack of documentation is not proof a feature is absent.

## What the market changes about our direction

Agent drawing, text grids, local execution and deterministic rendering already exist elsewhere. They are necessary capabilities, not defensible claims of uniqueness. Pixelbolt's useful position is a small, reproducible **asset compiler**: readable recipes, few agent tools, inspectable output, and dependable web/game exports. We need to prove that the complete workflow takes less setup and less corrective work.

The strongest competition is both established editors with automation and newer tools built directly for agents. We included small specialist repositories because their workflows are closer to ours; GitHub popularity was a filter for visual references, not a reason to exclude relevant competitors.

## What they get right, and where the fit breaks down

| Product | What they get right | Friction or limitation for our use case | What we should learn |
| --- | --- | --- | --- |
| **Aseprite + MCP adapters** | Mature pixel editor with Lua scripting and batch export. The `mattt` adapter keeps the agent surface to two tools and runs a full drawing script in one process. | Requires the Aseprite executable; that adapter also lists a licensed Aseprite copy and Go for building. More environment setup than a standalone recipe renderer. This is not evidence that its runtime is slow or that agents must click around. | Keep our tool surface small; support bulk operations; make eventual Aseprite interchange a bridge to human cleanup. [Aseprite CLI](https://www.aseprite.org/docs/cli/), [adapter](https://github.com/mattt/aseprite-mcp). |
| **light-vp/pixelart-mcp** | Local Pillow-backed drawing, text-grid read/write, shading helpers, named-part rigs, generated motions, and previews of changed regions. It explicitly teaches pixel-art craft. | Its documented rig workflow requires separating overlapping parts into a parts bin. That is a real authoring step. The Python/Pillow environment is an installation tradeoff, not inherently a flaw. Its claims of better model art quality need independent evaluation. | Named parts and small visual diffs are more valuable than asking the model to redraw every frame. This competitor is ahead of our first version in motion reuse and craft assistance. [Repository](https://github.com/light-vp/pixelart-mcp). |
| **ehm-93/pixel-mcp** | Indexed palettes, exact text views, cropped visual feedback, atomic undoable edits, persistence, tiled previews and advisory linting. | The README describes approximately 60 tools and several stateful concepts. That can increase discovery and sequencing work for an agent—an inference to test, not a measured failure. Default export scale is 4 unless overridden, which can surprise a native-resolution game workflow. | Copy the inspect/change/verify loop and clear export defaults. Our current full-recipe editing is less convenient than its targeted operations. [Repository](https://github.com/ehm-93/pixel-mcp). |
| **PixelLab** | High-level character generation, directional views, animation and connected tilesets through MCP/API. Handles much more of the artistic invention than our rasterizer. | Its docs require an active subscription for MCP and describe asynchronous generation, typically taking minutes. That is a poor fit for a fully offline, immediate edit loop; it is a reasonable tradeoff for model generation. | Borrow the meaningful asset concepts—character, action, terrain—and persistent identity. Do not claim our hand-authored sample proves comparable generative art quality. [Ways to use](https://www.pixellab.ai/docs/ways-to-use-pixellab), [MCP guide](https://api.pixellab.ai/mcp/docs). |
| **SpriteCook** | Style sets, character action presets, examples that expose actual animated assets, and agent integration. It communicates the final game asset rather than an abstract image prompt. | It is an account/credit-based hosted generation workflow. That does not meet our local-without-service-dependencies objective. Advertised style consistency and turnaround are vendor claims; we did not benchmark them. | Give users previews of actual actions and asset sets. Style consistency should become explicit shared palette/outline/scale settings. [Product](https://www.spritecook.ai/), [agent integration](https://www.spritecook.ai/agents). |
| **Piskel** | Low-friction browser editing, live playback, adjustable frame delay, PNG/GIF/sheet/ZIP output, and public source. | Its own download page describes offline releases as best-effort, with limited QA and potentially missing current fixes. That is a documented product gap, not a guessed issue. Its public workflow centers on direct visual editing rather than agent recipes. | Immediate preview and straightforward downloads matter. Keep browser and command-line rendering on one implementation so they do not drift. [Features](https://www.piskelapp.com/), [offline caveats](https://www.piskelapp.com/download/). |
| **Pixel Composer** | MIT-licensed node-based VFX editor for pixel art (GameMaker, GPU shaders, roughly 900 nodes; binaries are paid). Keyframes with easing and drivers on any input, a particle system, palette-aware dither, De-Corner/De-Stray cleanup, pixel-art scaling and rotation, Markov rewrite rules, and a headless CLI that runs a project's export nodes. | Built for people wiring graphs by hand. Its `.pxc` project is compressed JSON keyed by positional input indices, not a format to author as text. Many nodes are float filters (blur, bloom, chromatic aberration) or simulations and 3D that do not fit palette-exact sprites. | Borrow its pixel-art operations and particle model, not the graph: an agent already writes the procedural glue. Adopted 28 September 2026 (see below). [Repository](https://github.com/Ttanasart-pt/Pixel-Composer), [docs](https://docs.pixel-composer.com/). |
| **Pixelorama** | MIT-licensed editor with tilemaps, configurable UI, broad import/export, animation, project metadata and command-line export. | Its extensive editor is a different scope from a tiny agent toolkit. We have not established a performance or usability defect. The documented command-line export story alone does not demonstrate a complete headless authoring API. | Layer/frame metadata and good tile workflows deserve attention; avoid expanding into a complete desktop editor before the agent loop works well. [Official product page](https://orama-interactive.itch.io/pixelorama). |

## Adopted from Pixel Composer

Reviewed 28 September 2026 against its source at version 1.22. Both Pixelbolt showcases had hand-written the same helpers: Emberfall's generator has a seeded random-number generator, a polygon helper and trig-driven particle bursts; Tidewatch's `make-fx.mjs` has a particle loop, polar slash arcs and hand-coded dissolve patterns. Pixel Composer's node set covers those needs, so these ideas moved into Pixelbolt as text, deterministic and palette-exact:

| Pixel Composer | Pixelbolt | Adaptation |
| --- | --- | --- |
| Dither (Bayer 2/4/8, custom matrix, palette mode) | `dither` op | Two exact colours instead of nearest-palette search; canvas-anchored patterns, density ramps, `over` masks, erase. |
| Outline (inside/outside/middle, width, 3×3 directions) | `outline` options | Same placements and direction mask; the original 1px outside default is byte-identical. |
| De-Corner, De-Stray | `cleanup` patch change; per-frame counts in diagnostics | Proposed as ordinary corrections with a changed-pixel report, never applied on their own; right-angle corners are protected. Diagnostics count rather than flag them: 551 of the repository's 858 finished frames have L-steps the rule would change, and the ones we inspected were deliberate highlight strokes and rounded corners. |
| Scale Algorithm (Scale2x/CleanEdge with rotation) | pose part `rotate` | RotSprite-style: three Scale2x passes, rotated sampling, corner cleanup; baked into editable symbols. |
| Keyframe easing and drivers | pose `tween`, scene trajectory `ease` | Easing presets baked to whole pixels and degrees; no expressions. |
| Particle system (pSystem) | `pixelforge-fx` compiler | Seeded emitters baked into stamp/grid/line operations, seamless loops, dissolve; compiled output is an ordinary recipe. |
| Markov | `rewrite` op | Rules are palette-key text grids with rotation, mirroring, seeded chance and limits. |

Not adopted: the node graph and editor (AGENTS.md keeps the workflow text-first), float filters that invent colours, physics, fluid and 3D simulation, and expression or Lua scripting (the agent already is the scripting layer).

Validation: Tidewatch's effects recipe was rebuilt from a `pixelforge-fx` source ([report](reports/tidewatch-showcase-report.md#update-2-effects-rebuilt-with-the-particle-compiler)). The source is about the size of the particle code it replaced, but it is declarative, validated and tested for freshness, and it compiles to a recipe 43% smaller that reuses symbols. Hand-drawn frames (hit, sparkle) passed through unchanged.

## Reviewed: Pixel Art Lighter

Reviewed 12 October 2026 from Moonfell RPG's announcement video of version 3.2.8, which is not yet released, so no source was read. It loads a colour PNG, generates and edits a normal map and a "luminance" mask (how much light each pixel takes), and previews them under a point light with height, falloff, brightness, ambient and colour, with views of the lit image and of each pass.

| Pixel Art Lighter | Pixelbolt | Adaptation |
| --- | --- | --- |
| Generate a normal map | `pixelforge-normals` compiler | Each shape is rounded from its silhouette, with optional ramp-aware relief, and quantized to 17 named directions, so the result is an editable recipe aligned frame for frame. Every lit asset in our showcases had been drawn by a one-off script, and Tidewatch's pickups shipped a flat placeholder normal. |
| Modify the normal map | `patch` and overlays on the generated recipe | Direction keys are keypad digits and keyboard letters, so a fix is an ordinary grid edit that survives recompiling where frames are unchanged. |
| Light cursor with height, falloff, ambient and colour | Scene viewer light controls | Drag a light on the canvas; its height, radius and colour and the ambient light change live and save with the scene. |

Not adopted: the luminance mask, a material-mask pass (ramp lighting already leaves colours on no ramp, such as outlines, unlit, and brightens only within the palette); brightness above the authored colour (multiply lighting deliberately stops there); background detection (PNG import is lossless and does not guess a background); and reloading when files change on disk.

## Where Pixelbolt is already behind

The toolkit now has deterministic JSON recipes, palettes, text grids, symbols, frame inheritance, layers, PNG/APNG/atlas/CSS exports, a Canvas player, a local studio and eight MCP tools. Inspection supports region readback, silhouette, grayscale, onion and tile views, and advisory diagnostics; targeted patches include exact canvas-coordinate painting, regional edits and cleanup proposals. Immutable MCP recipe revisions survive restarts, and render previews show all frames or a selected animation's playback order. Pose sources, autotile templates and particle effect sources compile to ordinary recipes, and lossless PNG import brings externally edited art back. Remaining gaps include palette quantization, ready-made motion templates, persistent browser editing history, GIF export and native Aseprite interchange. Inline MCP contact sheets are static; exported APNGs and the HTML preview provide actual playback. (Updated 28 September 2026.)

A JSON-valid sprite can still be unattractive or animate badly. Automated tests and the independent binary decoder verify mechanics, not artistic quality or integration with every game engine. Aseprite, Pixelorama and Piskel also offer mature direct editing that this studio does not attempt to replace.

## Priorities

The local Emberfall exercise now provides a more specific [art-quality roadmap](reports/pixelforge-art-quality-roadmap.md), with source evidence, proposed editing and motion tools, acceptance criteria and a visual evaluation plan. It extends this review's priorities; it does not establish competitive art-quality superiority.

1. **Inspection and targeted corrections.** A bounded inspect operation returning a selected frame, contact sheet, cropped region or palette-character grid; a small patch operation with clear before/after feedback. Success: repair an eye in one frame without resending the complete recipe, and let the agent inspect all poses without a browser. *Status, 27 September 2026: built. Inspection (`pixel_inspect`, `pixelbolt inspect`) gives contact sheets, cropped regions and palette-key grids. Patching (`pixel_patch`, `pixelbolt patch`) applies atomic set/insert/remove edits and canvas-coordinate painting to a persistent revision, so an agent sends the recipe once, and reports every changed pixel with a before/after image. Render previews show every frame. Still open: comparing these workflows against competitors with the validation briefs below.*
2. **Reliable project recovery.** Autosaved browser drafts, explicit dirty/saved state, and undoable structured changes. Success: an accidental reload cannot discard a working recipe. *MCP recipe revisions now persist across restarts, including edits that have not been exported. Browser draft recovery remains separate work.*
3. **Helpful quality checks.** Empty frames, clipping, palette growth, isolated stray pixels, unexpected semi-transparency and tile-edge mismatch. Report findings as advisory with coordinates; legitimate artistic choices must not be rejected. *Status, 28 September 2026: built as advisory diagnostics (duplicate and empty frames, isolated pixels, colours outside the palette, loop jumps and per-frame cleanup counts), tile seam evidence in the tile view, and clipping locations in every validation. Unexpected semi-transparency is not reported yet.*
4. **Reusable motion.** Named parts and integer keyframes for bob, blink, recoil and walk templates. Keep pose substitution explicit where rotating pixels would damage the art. Measure authoring tokens and consistency against manual frame recipes. *Status, 28 September 2026: pose sources provide named parts, attachments, mirrored poses, rotated parts and eased tweens; ready-made bob, blink and walk templates are not built, and the token comparison has not been run.*
5. **Proven engine import.** A minimal Phaser and Godot fixture demonstrating frame slicing, pivots, timing and transparency. Add engine-specific export only where the generic atlas causes real friction.

Keep GIF support and PNG import as practical follow-ups. Defer a broad painting suite, cloud generation, accounts, collaboration and a large catalog of MCP tools. Optional external generators could eventually feed the same validation/export pipeline without becoming required dependencies.

## Validation before claiming an advantage

Compare the same four briefs across available tools: a 16×16 inventory icon, a 24×24 idle/walk character, a seamless terrain tile, and a precise revision to an existing frame. Fix palette size, native resolution and frame count. Record setup steps, tool calls, input/output tokens, elapsed time, unrequested pixel changes, successful engine import and a blind visual assessment. No speed, token-efficiency or quality superiority is established by this documentation review.

## Popular GitHub projects used for the dark studio direction

Rounded counts displayed by GitHub when checked: [Excalidraw](https://github.com/excalidraw/excalidraw) **133k**, [Penpot](https://github.com/penpot/penpot) **60.4k**, [Aseprite](https://github.com/aseprite/aseprite) **39.7k**. Counts are discovery signals, not quality scores; Aseprite is source-available under its own EULA, unlike the permissively/openly licensed references.

Excalidraw's public feature set emphasizes a canvas, dark mode, open JSON and local autosave. Penpot's [interface guide](https://help.penpot.app/user-guide/first-steps/the-interface/) separates the viewport, assets, properties and inspection. Aseprite grounds the interface in sprites, palettes and timelines. Our adaptation is a restrained charcoal workspace with clearly separated panels, a central canvas, frame strip, visible source and muted lavender selection states. These are design interpretations, not a copy of any project's code, artwork or exact theme.
