# Pixelbolt agent authoring guide

Create a small, editable JSON recipe; validate it; render it; inspect the PNG preview; revise the source. Use compact palette grids for silhouettes, symbols for repeated objects and inherited frames for small pose changes. The renderer is deterministic. It does not use an image model.

For visual quality decisions, regional corrections, pose compilation, scenes, material passes and PNG interchange, follow the [art workflow](art-workflow.md). These are supported extensions around version-1 recipes, not permission prompts or aesthetic guarantees.

For a moving character, use `bone` limbs with length/width profiles, a `mass` torso with squash, and `rows` for detailed heads and props. Declare dark-to-light `ramps` and world `light` (default 225°). Relative `angle` follows the parent; legacy `rotate` stays absolute. Attachments resolve in any order while parts paint in listed order. A two-bone `reach` targets a canvas point; grid `views` preserve authored detail at key angles.

Assign `rig` roles (`body`, `head`, `legs`, `arms`, `tail`, `ground`, `rest`) and add `motions` for idle, walk, run, jump, attack or hurt. Templates compile to ordinary recipes with named layers; `pixelbolt compile actor.poses.json --expand --out actor-edit.poses.json` exposes the generated poses. An authored pose with the same name overrides a generated pose. Keep the source authoritative and tune reach warnings, contacts and silhouette before export. [The full pose reference](art-workflow.md#structural-limbs-and-bodies) gives field ranges, defaults, points, joint rules and template parameters.

Use `pixelbolt inspect actor.poses.json --motion run --speed 48` or MCP `pixel_inspect` with `{source, view:"motion", animation:"run", speed:48}`. A compiled recipe/revision needs explicit `metadata` from `pixel_compile` with `metadata:true`. Review slide, signed ground error, key-pose spread and joint loop seams; missing information is reported as unavailable. Contact checks sample frame onsets, not continuous travel during a held frame. In the studio, open the pose source, select **Motion** or **Show contacts**, and keep **Travel (px/s)** separate from playback speed.

## Project

Required: `version: 1`, `name`, `width`, `height`, `frames`.

- `name`: starts with a letter, then letters, numbers, hyphens or underscores; at most 64 characters. Frame, symbol and animation names follow the same convention. Windows device names (CON, PRN, AUX, NUL, COM1–9, LPT1–9) are reserved. Frame and animation names must also be unique ignoring case so bundles work on case-insensitive filesystems.
- `width`, `height`: integers from 1 to 256.
- `palette`: map names to literal `#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA` or `transparent`. Single-character keys are usable in grids. Palette values cannot reference other palette entries. `.` and space are reserved for skipping pixels; `transparent` is reserved. Grid characters must be single UTF-16 code units (letters such as `À` work; emoji do not).
- Shared palettes: `"palette": { "$ref": "../palette.json", "x": "#fff" }` loads a palette file (a flat map, or any JSON with a `palette` map) relative to this recipe; local entries add to or override it. The CLI and MCP resolve references before rendering (MCP only inside its `--root`). The pure renderer rejects unresolved references. `patch --out` keeps the reference and writes only new or changed entries locally.
- `background`: palette name or color; defaults to transparent.
- `ramps`: optional lists of palette keys from dark to light, one per material: `[["k", "s", "t", "u"], ["f", "g", "h"]]`. `shade` and scene ramp lighting move a colour along its ramp instead of inventing a darker one, so shading keeps the palette. A key belongs to one ramp; a colour shared by keys in two ramps follows the first. A shared palette file written as `{ "palette": {...}, "ramps": [...] }` supplies ramps to every recipe that links it and declares none of its own.
- `anchor`: optional `[x, y]` pivot shared by every frame (frames may override it). The atlas exports it as `anchor` in exported pixels and `pivot` = anchor ÷ source size, the TexturePacker convention Phaser reads. `[x, y]` names the top-left corner of that pixel.
- `symbols`: map names to equal-width string arrays. A symbol is a reusable palette grid.
- `frames`: 1–256 frames. At most 4,194,304 total source pixels. Frame order sets atlas order; when a script generates frames from an object, remember that JavaScript lists integer-like keys (`"0"`, `"7"`) before all others, so build the list from an array when order matters.
- `animations`: map names to `{frames: [frame names], direction?, loop?}`. Omit for a default animation using all frames. `direction` is `forward` (default), `reverse` or `pingpong`. Pingpong excludes repeated endpoints: a,b,c becomes a,b,c,b. `loop` defaults to true; false plays once and holds the last frame.
  ZIP32 bundles require animation count + frame count + 7 support files ≤ 65,535. Validation rejects overflow before rasterizing frames; at most 65,527 animations fit with one frame. Each input sequence has at most 1,024 references before pingpong expansion.
- `sheet`: `{columns, padding, scale, trim}`. Defaults: up to 8 columns, 0 padding, scale 1, untrimmed. Padding surrounds **each** cell on every side, so the distance between adjacent contents is twice the padding. Padding and dimensions are multiplied by the integer scale. Scale 1–16; columns 1–256; padding 0–16. Atlas area must be at most 16,777,216 pixels. `trim: true` packs each frame by its visible bounds (deterministic shelf packing; `columns` is ignored); atlas entries report `trimmed: true` with `spriteSourceSize` offsets inside the unchanged `sourceSize`. Individual frame PNGs and APNGs stay full-canvas, and the CSS export switches between `frames/*.png` instead of sliding an atlas background.

Use `node bin/pixelbolt.js schema` for the complete JSON Schema. Unknown fields are errors so misspelled instructions do not disappear silently. Omit optional fields to use defaults; null is not accepted.

In the portable Pixelbolt Studio build, run `.\pixelbolt` on Windows or `./pixelbolt` elsewhere from the build folder instead of `node bin/pixelbolt.js`.

## Frames and layers

A frame is `{name, duration?, from?, translate?, wrap?, flipX?, flipY?, palette?, anchor?, points?, ops?, layers?, pixels?}`.

`duration` is 1–60000 milliseconds, default 100. `from` copies an **earlier** frame; otherwise the frame starts with the project background. Whole-frame flips happen first, then `translate: [dx, dy]`, then `ops`, then layers in array order, then final `pixels` corrections. Translation leaves newly exposed pixels transparent and clips at the canvas boundary; with `wrap: true` pixels scroll around the canvas instead (animated water, conveyors, clouds).

`palette` recolors project palette keys for this frame's own drawing: `{"!": "w", "@": "tint2"}`. Keys must exist in the project palette; values are colors or project palette names. This is palette cycling: stamp the same symbol in every frame and give each frame a different mapping, with no marker colors or `replace` passes. `anchor` overrides the project anchor; `points` names up to 64 positions (`{"hand": [12, 9], "advance": [6, 0]}`) exported per frame in the atlas, in exported pixels. Inherited frames do not copy their source frame's anchor, points or palette.

Layers are `{name?, visible?, opacity?, x?, y?, palette?, ops?}`. They render to a transparent buffer of the **canvas size**, then translate by x/y, then composite in order with source-over alpha. `opacity` is 0–1, applied once to the flattened layer. Hidden layers are validated but not composited. Drawing outside a layer's own canvas is clipped **before** the layer is translated.

A layer `palette` recolors project palette keys for that layer's own drawing, on top of the frame's `palette`: `{"layers": [{"name": "panel", "ops": [...]}, {"name": "glow", "palette": {"r": "#ffffff"}, "ops": [...]}]}` flashes the glow white while the panel, drawn with the same key `r`, keeps its colour. Keys must exist in the project palette; values are colors or project palette names (resolved against the project palette, not the frame's). Use it for a strobe, a hit flash or a cycle on one part of a frame; the frame's `ops`, other layers and `pixels` corrections keep the frame's colours. Diagnostics count the colours it introduces as declared.

Transparent drawing skips pixels. Use `clear` to erase. Clearing a layer erases only that layer's own pixels; it does not erase underlying layers. A `from` frame is already flattened, so later operations can edit or erase its pixels.

`pixels` is an optional list of `{x, y, color}` corrections in **final canvas coordinates** (top-left origin). Each entry replaces the exact RGBA after all operations and layers: `transparent` erases even underlying layers; a semi-transparent color sets that exact alpha instead of blending. Coordinates are required integers inside the canvas, colors use palette names or hex, and later entries at the same coordinate win. At most 65,536 entries are allowed per frame. Original layer operations are preserved. Frames that inherit this frame also inherit its corrections before applying their own transforms. Remove a correction to reveal the original drawing beneath it. Use `pixel_patch`'s `paint` change to manage these corrections without knowing the layer structure.

## Operations

Coordinates are integers; origin is the top-left; positive y points down. x/y default to 0. Coordinates are limited to -4096–4096. Shapes with positive w/h extend w/h pixels including their origin. Out-of-bounds drawing is clipped with a warning that names the first location; `clipping` (validate, inspect, patch and render results) lists every operation, translation or layer offset that clipped, with a pixel count, e.g. `{"path": "project.frames[2].ops[0]", "pixels": 3}`. Explicit false/zero values are honored.

| op | Properties | Behavior |
| --- | --- | --- |
| `pixel` | x, y, color | One pixel, source-over alpha |
| `rect` | x, y, w, h, color, filled? | Filled by default; false draws a 1px outline |
| `ellipse` | x, y, w, h, color, filled? | Pixel-center ellipse inside the bounding box |
| `line` | x, y, x2, y2, color | 1px integer line; both endpoints included |
| `clear` | x, y, w, h | Set a rectangle to fully transparent black |
| `fill` | x, y, color | Four-connected flood fill matching the seed's exact RGBA; replaces RGBA |
| `replace` | from, to | Replace every exact RGBA match in the current buffer |
| `grid` | x, y, rows, scale?, flipX?, flipY?, rotate?, remap? | Draw palette rows; dot and space skip |
| `stamp` | x, y, symbol, scale?, flipX?, flipY?, rotate?, remap? | Place a named symbol |
| `text` | x, y, text, color, align?, spacing?, lineHeight?, scale?, flipX?, flipY?, rotate? | Text in the built-in pixel font |
| `copy` | x, y, symbol \| from, sx?, sy?, w?, h?, scale?, flipX?, flipY?, rotate?, remap? | Copy a rectangle of a symbol (palette characters) or an earlier frame (exact RGBA, optionally swapped) |
| `autotile` | x?, y?, symbol, mask, mode?, remap? | One autotile tile: the four quarters of a template symbol that a neighbour mask selects |
| `tilemap` | x?, y?, tile, rows, legend, outside?, empty?, classes?, seed? | A character map drawn from this recipe's symbols and autotile templates, with variants, weights and neighbour rules |
| `outline` | color, diagonal?, position?, width?, directions? | Outline every visible pixel in this buffer: outside rings, inside edge rings or both, in chosen directions |
| `dither` | x?, y?, w?, h?, color \| erase, density?, direction?, pattern?, offset?, seed?, scale?, over? | Ordered, noise or value-noise dither: draw (or erase) where a canvas-anchored threshold pattern is below the density |
| `shade` | x?, y?, w?, h?, steps?, shape?, density?, direction?, pattern?, offset?, seed?, scale?, over? | Move pixels along their colour's ramp: shadows and light that keep the palette on any surface |
| `rewrite` | x?, y?, w?, h?, rules, empty?, steps?, chance?, limit?, seed?, rotate?, mirror? | Markov-style rewrite rules: small match grids replaced wherever they occur, in a seeded order |

Rectangle/ellipse/clear w/h are integers 1–512. Grid and symbol rows must be rectangular, at most 256×256 characters, and use defined palette keys. Grid/stamp/copy scale is 1–16. Flip X/Y before rotation; rotation is 0, 90, 180 or 270 degrees clockwise; then scale. x/y locates the transformed grid's upper-left corner. Geometry is never anti-aliased.

`text` draws the built-in font: printable ASCII, the accented letters of western European languages (À–ÿ, including ß, æ, ø, ñ and ç, and Œ œ Š š Ž ž Ÿ) and the symbols ¡ ¿ « » ‹ › ° © ® £ € ¥ ¢ · × ÷ ± – — … ‘ ’ ‚ “ ” „ •. Capitals are 7 pixels tall, lowercase 5, descenders 1 below the baseline, so a line is 8 rows and `y` is the top of the capitals; the accent of a capital (É, Ñ, Ü) reaches 2 rows above `y`, so leave that room above the first line; on later lines the accent uses the gap between lines. Glyphs are as wide as their ink (1 to 5 pixels), digits are always 5 so counters do not jitter, and a space is 3; with the default `spacing` of 1 a line of n characters is about 6n pixels wide, so 40 characters fit a 240-pixel canvas. `\n` starts a new line (default `lineHeight` 10). `align` says what `x` is: the `left` edge (default), the `center` or the `right` edge of the text, and lines align the same way. `scale`, flips and rotation work as for grids. A character the font lacks (other scripts, emoji) is an error that names it; draw those yourself with `grid`. Text that overhangs the canvas is clipped and reported like any other drawing. `measureText(text, { spacing, lineHeight })` from `src/font.js` returns the width, the height and `top` (0, or -2 when an accented capital on the first line needs the rows above) before you draw. Use `outline` after it for a readable edge on busy backgrounds.

`remap` recolors grid characters for one operation only, `{"1": "4", "2": "#ffffff"}`: one authored shape, several color variants. `copy` takes `sx, sy, w, h` from its source (defaults: the whole source) and draws it like a stamp; it is what lets one template symbol hold every autotile quarter. Frame copies keep exact RGBA; their `remap` swaps exact colours instead of characters, with keys that name a colour by project palette key (any length) or hex: `{"op": "copy", "from": "walk-1", "remap": {"k": "r", "#ffffff80": "glow"}}` recolors a copied pose for a hit flash. Keys resolve against the project palette, so they match a pose drawn with it; values resolve like any other colour in the frame. A key cannot be transparent (frame copies skip transparent pixels), and two keys cannot name the same colour. `outline` works on the buffer it is in: frame `ops` outline everything drawn so far (including an opaque background, which leaves nothing to outline), layer `ops` outline only that layer. The default is 4-connected; `diagonal: true` also fills corners. Stamp clusters in a layer and finish with `outline` to get one silhouette around their union.

`autotile` draws one tile of an autotile set from a template symbol two tiles wide and three tall (see [autotile templates](art-workflow.md#autotile-templates)): the four quarters that `mask` selects. `mode` is `blob` (default; N=1, NE=2, E=4, SE=8, S=16, SW=32, W=64, NW=128, reduced so a diagonal counts only when both of its sides match) or `cardinal` (N=1, E=2, S=4, W=8). The autotile compiler emits one per frame, so a compiled frame reads as its mask and editing the template redraws every tile.

`outline` options: `position` is `outside` (default), `inside` (recolor the shape's own edge pixels) or `middle` (split the width; an odd pixel goes outside). `width` (1–8) adds rings. `directions` is a 3×3 grid centred on a visible pixel, with a dot in the centre, whose `x` marks the sides that get the line: `["...", "...", "..x"]` outside is a drop shadow (with `width: 2`, a longer one), and `[".x.", "...", "..."]` inside recolors only edges whose upper neighbour is transparent, a top rim light. It replaces `diagonal`. The canvas edge does not count as transparent, so a shape cut by the canvas gets no inside line there.

`dither` draws `color` (or clears, with `erase: true`) where an ordered threshold pattern is below `density`. x/y default to 0 and w/h run to the canvas edge. `density` is 0–1 (default 0.5) or `[from, to]`, ramping along `direction`: `down` (default), `up`, `right`, `left` or `radial` (centre to edge). `pattern` is `bayer2`, `bayer4` (default), `bayer8`, `noise`, `value` or a custom matrix of ranks; low ranks turn on first, and a highest rank n gives n + 1 levels, so `[[0, 1], [1, 0]]` is a checkerboard at 0.5 and `[[0], [1]]` gives stripes. `noise` is seeded white noise with no period, for large areas, fades and dissolves where a Bayer grid would show; `seed` (0–2147483647, default 0, only with `noise` or `value`) chooses its order. `value` is seeded smooth noise: neighbouring thresholds are close, so a density draws connected clumps about `scale` pixels across (1–64, default 4) instead of speckle, for moss, rubble or grass patches. Its thresholds are equalized, so density is still the share of a large area that is drawn; `{"op": "dither", "x": 8, "y": 40, "w": 44, "h": 30, "color": "n", "density": [0.9, 0], "direction": "radial", "pattern": "value", "scale": 5, "seed": 3, "over": "g"}` grows a moss patch on the floor colour that thins toward its edge. Each pixel keeps its threshold for a seed, so raising `density` frame by frame dissolves pixels in one fixed order with no flicker, and a new seed per frame makes the noise boil. The noise is a seeded integer hash, the same on every engine. Patterns follow canvas coordinates, so neighbouring dithered areas line up; `offset: [dx, dy]` shifts the pattern (crawl it between frames). `over` limits the change to pixels of listed exact colors, so `{"op": "dither", "x": 24, "w": 8, "color": "S", "density": [0, 1], "direction": "right", "over": "s"}` is a shading band that never spills outside the stone color. Use dithering for transitions and bands, not for whole surfaces.

`shade` moves every pixel of its region `steps` along its colour's ramp (see `ramps`): −1 (the default) is one step darker, positive steps lighten, and the ends of a ramp clamp. A shadow is then right on any surface: `{"op": "shade", "shape": "ellipse", "x": 30, "y": 62, "w": 10, "h": 4}` darkens floor, moss and brick under a barrel each within its own colours. Colours on no ramp stay as they are, transparent pixels stay transparent, and diagnostics find no new colours. The region, `over` and the density field work as for `dither`, with a default density of 1; a radial `[1, 0]` density with `pattern: "value"` gives a pool of light or shadow a ragged edge. `shape: "ellipse"` keeps to the ellipse inside the region. A recipe without ramps cannot shade.

`tilemap` draws a whole character map into the buffer, so later operations see the composed room: a `dither ... over` the floor colour grows moss only on the floor, a `shade` darkens whatever a shadow lands on, and `rewrite` rules can find corners. `tile` is the cell size; `rows` are equal-width strings where dot and space are empty cells; `legend` maps each other character to a `symbol` drawn at the cell, `symbols` (variants picked by cell position, optionally `weights`), or an autotile `template`/`templates` with `autotile: "blob"` or `"cardinal"` and an optional `match` string of characters counted as the same terrain. A legend entry of `null` is a context cell: never drawn, but counted by masks and rules. The legend and rules are the same as in scene tilemaps (see [the art workflow](art-workflow.md#scene-and-tile-review)):

```json
{ "op": "tilemap", "tile": [8, 8], "empty": "~", "rows": ["WWWW", "WFFW", "WWWW", "...."], "legend": {
  "F": { "rules": [
    { "symbols": ["floor-0", "floor-1"], "weights": [3, 1] },
    { "where": [".W.", "...", "..."], "symbol": "north-face" }
  ] },
  "W": { "rules": [
    { "templates": ["cap", "cracked"], "weights": [2, 1], "autotile": "blob" },
    { "where": ["...", "...", ".~."], "symbol": "cliff", "offset": [0, 1] }
  ] }
} }
```

Here a floor cell draws a floor variant and, when a wall lies above it, the wall's north face over it; a wall draws its cap and, when nothing lies below it, a cliff into the empty cell beneath.

`rewrite` applies up to 16 rules `{match, replace}`: equal-size grids of up to 8×8 palette keys. In `match` a dot or space matches anything; in `replace` it keeps the pixel. Choose an `empty` character (not a palette key) to match transparent pixels and to erase. Each step applies every rule in order: its matches are found on the pixels as they were when that rule started and applied in a seeded order, skipping any that would read or write a pixel the rule already rewrote in that step, so two overlapping fixes never both apply. `steps` (1–64, default 1) repeats, stopping early when nothing changes. `chance` (0–1) and `limit` (per rule per step) thin the matches; `seed` makes the result reproducible. `rotate` also matches the rules turned 90°, 180° and 270°; `mirror` also matches them flipped horizontally. Rewrites set exact colors. Example: moss on exposed tops, `{"op": "rewrite", "empty": "_", "rules": [{"match": ["_", "k"], "replace": [".", "m"]}], "chance": 0.7, "seed": 2}`. See `examples/shrine.json` for cracks, moss, dithered bands, a shading band, a rim light and a drop line.

## Inspecting

Look at every frame before exporting. Inspection renders its images in memory; the CLI saves the contact sheet only when given `--out file.png`. MCP inspection also saves an immutable recipe revision for later calls, without exporting assets.

- **Contact sheet**: one PNG with the selected frames left to right, top to bottom, on a neutral checkerboard with dark gutters. The response lists each cell's frame name and duration, plus the layout (`columns`, `rows`, `scale`, `gap`). The default is every frame in project order. `animation` shows one sequence in playback order, including reverse and pingpong. `frames` lists frame names in any order. The automatic scale is the largest, at most 16, that keeps each cell within 256px and the sheet within 1024px. `scale` (1–16) overrides it, up to a 4096px sheet. `background` is `checker` (default), `transparent`, a palette name or a hex color, such as your game's backdrop.
- **Palette-key grids** (`grid: true`, CLI `--grid`): each distinct selected frame read back in the recipe's grid format. A pixel whose exact RGBA matches a single-character palette key shows that key; `.` is fully transparent. Any other color, whether a multi-character palette name, a literal hex color or a semi-transparent blend, gets a legend symbol: a digit, letter or punctuation mark that is not a palette key. Symbols belong to the recipe, not the request: multi-character palette names come first, in palette order, then other colors in the order frames use them. Every readback of the same recipe therefore agrees, and each response lists only the symbols it uses. `?` counts any colors left once the symbols run out. Grids are limited to 16,384 pixels in total. MCP prints them with x/y rulers; the CLI returns JSON `rows` that start at the region's top-left corner.
- **Region** (`region: {x, y, w, h}`, CLI `--region x,y,w,h`): crops every cell and grid to a canvas rectangle. Smaller regions are shown larger, so you can compare a face across a blink or read the pixels around a joint without printing the whole canvas.
- **Patterns and strides**: in `frames`, `*` matches any run of characters and `?` one character, so `"flash-*"` (CLI `--frames 'flash-*'`) selects every matching frame in project order. `step: n` with optional `offset: k` (CLI `--step n --offset k`) keeps every nth cell of the selection, frames or animation positions, from position k (counting from 0). Use it for long cycles with a repeating structure: in a strobe that alternates A and B frames, `step: 2` shows only the A frames and `step: 2, offset: 1` only the B frames, where `maxCells`'s evenly spaced samples would alias between them. The stride applies before `maxCells`; `sampling` reports `step`, `offset`, the original positions and the method.

- **Art review**: `view: "silhouette"|"grayscale"|"onion"|"tile"` (default `color`), `native: true`, `diagnostics: true`, and `maxCells: 1..256`. Onion requires an animation and shows pink previous/cyan next neighbors by playback position. Tile repeats each selected frame 3×3 and adds `tiles`: per-axis `doubledRows`/`doubledColumns` (a line on both opposite edges that doubles when repeated), `wrapSteps` versus `interiorMaxSteps` (large value steps across the wrap versus across the busiest interior boundary) and a `suspicious` flag. A stroke that merely touches one edge is not flagged; the image is the evidence. Native adds a second 1× image. Diagnostics are advisory and include timing evidence and per-frame `corners`/`strays` counts (pixels a `cleanup` change would alter); sampled previews report original positions and omissions. Exact grids always use source colors. CLI flags: `--view`, `--native`, `--diagnostics`, `--max-cells`.
- **Isolation/comparison**: `layers: ["body"]` isolates named layers (excluding unassigned canvas ops/corrections), and `reference: "revision-id"` compares to a saved recipe. CLI: `--layers body` and `--reference previous.json`. See the [detailed semantics](art-workflow.md#inspection-options).

## Patching

Change a recipe with small edits instead of rewriting it. Over MCP, send the full recipe once: every successful response from `pixel_validate`, `pixel_inspect`, `pixel_patch` and `pixel_render` includes a `revision` id, and those tools accept `revision` in place of `project`. Revisions are immutable recipe snapshots saved in `<MCP --out directory>/.revisions/`, including edits that have never been exported. Restart with the same output directory to keep using earlier ids as undo points. Use an absolute `--out` path so changing the working directory does not change the store. Older ids can also be recovered from recipes in existing render folders under that directory. Unknown or damaged revisions produce an error; stored snapshots are never silently replaced. Snapshots are retained until you explicitly remove their files; keep the output directory backed up. The CLI patches files instead.

`changes` apply in order:

| Change | Effect |
| --- | --- |
| `{"set": path, "value": v}` | Replace a value, or add an object field |
| `{"insert": path, "value": v}` | Insert into a list before the selected item; `[-]` appends |
| `{"remove": path}` | Delete an object field or list item |
| `{"paint": "frames[blink]", "value": [{"x": 9, "y": 7, "color": "k"}]}` | Set exact pixels in final canvas coordinates after all layers; `transparent` erases |
| `{"grid": "frames[blink]", "value": {"x": 9, "y": 7, "rows": [".kk", "~k."], "erase": "~"}}` | Compact correction; dots/spaces preserve, explicit erase clears |
| `{"move": "frames[blink]", "value": {"x": 9, "y": 7, "w": 3, "h": 2, "dx": 1, "dy": 0}}` | Move selected RGBA, clearing source; overlapping moves retain corrections |
| `{"recolor": "frames[blink]", "value": {"x": 9, "y": 7, "w": 3, "h": 2, "from": "k", "to": "g"}}` | Recolor exact matches in a region |
| `{"cleanup": "frames[run-2]", "value": {"corners": true, "strays": true}}` | Propose fixes for doubled corners and stray pixels as canvas corrections |

Regional actions accept an optional matching `mask` (`x` selects, `.` preserves). Canvas actions accept `scope: "frame"` or `"inherited"` (default); frame scope records compensating literal-color corrections on affected dependents and reports them. Named selections and guarded rebuilds use [overlay sidecars](art-workflow.md#rebuild-safe-overlays).

`cleanup` reads the rendered frame and writes ordinary `pixels` corrections, named by palette key where one matches. `corners` removes the corner pixel of an L-shaped step in a one-pixel line (a "double"), giving it the colour outside the step; filled areas and right-angle corners whose arms are longer than one pixel are left alone. `strays` gives a pixel the colour all eight of its neighbours share: noise in a fill, pinholes and isolated specks. At least one must be `true`. Optional `x, y, w, h` and `mask` limit where pixels may change, and `colors` limits which original colours may change. The edit reports `corners` and `strays` counts, and the comparison lists every pixel, so check it: eyes, sparks and deliberate corners are legitimate. `inspect --diagnostics` counts, per frame, how many pixels each option would change. They are counts rather than findings because most L-steps and specks in finished, hand-drawn art are deliberate; they matter most for rotated, rewritten, compiled or imported frames.

Paths use the same form as error paths, with an optional `project.` prefix: `frames[3].duration`, `palette.k`, `symbols.mossling[9]`, `sheet.padding`. In a list, `[name]` selects the item whose `name`, or string value, matches, and `[-]` is the end: `frames[blink].layers[body].ops[2].x2`, `animations.idle.frames[-]`. Quote unusual keys: `palette["dark.green"]`. Intermediate fields must exist, except that an insert can create the list it inserts into; `set` may add the final object field. Frame `ops` draw before the frame's layers. Use `paint` to correct the visible result directly; use `set` or `insert` inside layer `ops` when changing how that layer is drawn.

`paint` accepts a frame path by name or index and 1–65,536 `{x, y, color}` entries. Coordinates match inspection grids, with no layer-offset conversion. It updates the frame's `pixels` corrections, retaining only the last correction at each coordinate. Palette references stay editable. Remove `frames[blink].pixels` to reveal that frame's original drawing, or use an earlier revision to undo the whole patch.

A patch is atomic: if any change fails, or the result does not validate, the source and earlier revisions stay unchanged and no result revision is saved. MCP saves successful base and result revisions; the CLI saves only the outputs requested by flags. Patching reports:

- `edits`: each change with its resolved index path (`at`) and the value it replaced (`before`), or `created`. Paint edits report the number of submitted pixels; the comparison below reports their visible effects.
- `frames.changed`: every frame whose pixels differ, including frames that inherit from an edited frame, with a pixel count and bounding box. Up to 16 changed pixels are listed with canvas coordinates and palette-key characters (`from`, `to`); larger changes are summarized as color transitions. `unchanged`, `added`, `removed` and `durations` complete the picture, and `animations` lists changed sequences and loop settings.
- A before/after PNG (MCP) with one row per changed, added or removed frame: before on the left, after on the right. It is cropped to the changed area plus 2 pixels when no frames were added or removed.

CLI: `node bin/pixelbolt.js patch sprite.json --changes fix.json` previews the report. `--changes -` reads the changes from stdin as a JSON list. Add `--out sprite-v2.json` to save the patched recipe and `--image diff.png` for the before/after image; existing files are kept unless you pass `--force`.

## Efficient workflow

1. Use a 16×16 or 24×24 canvas and 4–8 colors. Establish the silhouette as a readable grid.
2. Save repeated components as symbols. Name colors semantically for shape operations; use one-character palette keys in grids.
3. Build one good resting pose. Create frames with `from` for small changes, or stamp body parts in separate layers for movement.
4. Start at 80–200ms per frame. Add holds intentionally by increasing a pose's duration. Group sequences by behavior: idle, walk, jump, impact.
5. Validate, inspect, patch, repeat; render when the art is right. A valid JSON document can still have a bad silhouette, wrong facing or a jerky loop. Check each animation's contact sheet, read a region grid before editing exact pixels, and confirm each patch changed only the pixels you meant to change.
6. Save the JSON source with the output bundle. Inherit poses instead of repainting the entire image where possible.

## Calling the tool

CLI: `node bin/pixelbolt.js inspect sprite.json --out sprite-frames.png`, optionally with `--animation idle` or `--grid --region 4,6,8,6`; `node bin/pixelbolt.js patch sprite.json --changes fix.json --out sprite-v2.json` for targeted edits; then `node bin/pixelbolt.js render sprite.json --out output/sprite`. Files that `compile`, `autotile`, `import` and `overlay` generate, and the examples, use compact formatting: anything that fits in 120 columns (a frame, an operation, an animation) stays on one line, and pixel grids keep one row per line.

CLI sharing is opt-in: `pixelbolt share <recipe.json|->` prints a playground link; `render` and `scene` accept `--embed-recipe`, and `import image.png --embedded --out recipe.json` recovers its source. MCP `pixel_render` accepts `share: true` and `embedRecipe: true` for the same resolved recipe. Links carry the recipe text and engine version in the URL fragment, which browsers do not send to a server; PNGs carry them in a compressed recipe chunk.

MCP: call `pixel_help` once for a short quick start. Its `topic` returns one longer document when you need it: this guide (`guide`), the [art workflow](art-workflow.md) (`workflow`), the recipe's JSON Schema (`schema`), a complete recipe (`example`), or a source format's schema (`poses`, `scenes`, `autotile`, `fx`, `fluid`, `normals`). The tools describe `project` only briefly; the server checks every recipe and names the path of any mistake. Send `{ "project": <recipe> }` to `pixel_inspect` (plus any inspection options) or `pixel_validate`, a cheaper check without images. Afterwards pass `{ "revision": <id> }` instead of the recipe, and use `pixel_patch` for edits (or `overlay` to apply a saved correction overlay). When the art is right, call `pixel_render` with the revision. Rendering returns the output `directory`, the key files relative to it (sheet, atlas, `name.pixel.json`, CSS, player, preview and animations), `frames`/`animations` counts, and a PNG contact sheet of **every frame**; pass `listFiles: true` for every path. Its `preview` metadata gives the region, sheet layout and cell names/durations. Add `"animation": "idle"` to preview that sequence in expanded playback order, including repeated poses; all animations are still exported. The inline preview is static; exported APNGs and `preview.html` play the animation. Every render gets a unique output directory, so iterations do not overwrite earlier results.

`pixel_compile` turns a `pixelforge-poses` source, a `pixelforge-autotile` template, a `pixelforge-fx` particle source, a `pixelforge-fluid` source (simulated smoke, fire, explosions, steam, magic, water and thick liquids such as honey and slime; see [fluid effects](art-workflow.md#fluid-effects)) or a `pixelforge-normals` source into a recipe revision with a contact sheet (`metadata: true` adds pose attachments and markers, the autotile mask table, particle counts, fluid peaks and per-frame pixel counts, or the normal directions and their pixel counts). A normals source derives a lighting normal pass from a colour recipe given inline, as a file inside the root or as `{"revision": id}`; see [generated normal passes](art-workflow.md#generated-normal-passes). `pixel_scene` renders a `pixelforge-scene` manifest at a time and returns the image with placements and warnings; assets may be inline recipes, files inside the server root or `{"revision": id}`, and `export: true` writes a replayable scene bundle. `pixel_import` turns a base64 PNG (`data`) or a file inside the root (`path`) into a lossless recipe revision. Requests may be up to 16 MiB; an oversized request gets a JSON-RPC error and the server keeps running.

For an interactive web page, `createLiveFluid(source, { effect, warmup })` from `pixelbolt/fluid` runs one effect of a fluid source live, a frame at a time, instead of baking a recipe. `step(n)` advances it; `push({ x, y, vx, vy, radius })` stirs the flow; `puff({ x, y, radius, density, temperature })` adds or takes away smoke, heat or water; `boost(name, strength, frames)` scales a named emitter for a while; and `render()` returns `{ rgba, keys }`, drawn with the effect's own look. It makes the same checks as `compileFluid` before simulating and runs the same simulation, so the same calls give the same pixels in every engine. A 128 × 60 steam plume steps in about 8 ms on a desktop CPU. See [live fluids](art-workflow.md#live-fluids).

Exports include a TexturePacker-style RGBA atlas, named sequences, exact durations, individual frames, APNGs, CSS and a Canvas player. Every render reports a `check` of what it delivered: the size of each exported frame (the canvas times `sheet.scale`), each animation's frame count and loop, the colours used (fully transparent pixels are not colours), whether the frames are transparent, the GIF size, and frames that are fully transparent. Give it what the user asked for, as MCP `pixel_render`'s `expect` or `pixelbolt render --expect '<json or file>'` (`width` and `height` of each frame, `frames` per animation, at most `colors`, `transparent` for the background, `loop`, and over MCP `gifScale`, the GIFs' enlargement over the asked frame size, since `render` writes no GIFs), and `check.ok` says whether the files match, with one entry in `check.problems` per mismatch: the file, what was asked, what was delivered and the patch or render call that fixes it. GIFs are checked against the asked size when `width`, `height` or `gifScale` is given, and against `transparent` and `colors`: a GIF `background` makes an opaque GIF with a colour of its own. With `animation` (CLI `--animation`), only that animation and its frames are checked. The check reads the export and never changes it. Its fixes stay inside the format's limits: a size over 256 px a side becomes a smaller canvas at a whole `sheet.scale` (the one nearest the drawing, and the most detailed), more than 256 frames come from an animation that repeats frame names (up to 1,024 names, or 2,046 frames as a pingpong), and an opaque background that frame drawing erases names the `clear`, erasing `dither`, `translate` or `"transparent"` pixels that do it; a fix that would pass the exporter's pixel budgets (frames, atlas, animations, GIFs) says so instead. `delivered.partlyTransparent` reports pixels that are only partly transparent. Before making frames for video, `pixelbolt validate <recipe> --fps 30` (MCP `pixel_validate` with `"fps": 30`) adds `frameGrid`: the frames whose durations are not whole video frames (with how many frames they are), and for each animation the positions a sequence would lengthen, shorten or never show, the pass length in video frames, whether a loop `closes` on the grid and `loopsThatFit` when it does not. It predicts exactly what `sequence` writes without writing anything. For sharing where only GIF animates, `pixelbolt gif <recipe> --out <new.gif> [--animation name] [--scale 1-16] [--background color]` or MCP `pixel_render` with `"gif": {}` writes GIFs beside the bundle, at the frames' own size unless a scale enlarges them: exact colours and never quantized (a frame needing more than 256 colours is an error), 1-bit transparency at 50% alpha unless a background colour blends it, and delays in 10 ms steps (20 ms minimum). Read the returned `notes`; use APNG or the atlas when alpha or timing must be exact. `pixelbolt gif-frames <folder> --fps 25 --out <new.gif> [--loops 0] [--background color] [--prefix name_]` makes a GIF from a folder of numbered PNG frames (`name_0001.png` …, from `sequence`, a video tool or an editor) by the same rules, one GIF frame per file in number order. It never quantizes: a frame over 256 colours is refused by name, and frames whose colours differ across the loop each carry their own colour table, so thousands of colours over a loop stay exact. Frame k starts at k × 1000 / fps ms rounded to centiseconds, so 25 fps is 40 ms per frame, 30 fps alternates 30 and 40 ms and keeps the loop's length, and above 50 fps delays are raised to 20 ms (reported). `--loops` is the number of plays, 0 (default) for ever. Without transparency, frames after the first store only the rectangle that changed. The result reports the delays used, colours per frame and in all, gaps in the numbering, other PNGs left out and notes. The PNGs must be 8-bit RGB or RGBA, all the same size and at most 4096 pixels a side, and 134,217,728 pixels (115 frames at 1080 × 1080) and 18,000 frames in all. For a video editor, `pixelbolt sequence <recipe|source|scene> --out <new folder> --fps 30 --size 1080p` (or `"sequence": { "fps": 30, "size": "1080p" }` on MCP `pixel_render` and `pixel_scene`) writes one PNG per video frame with straight alpha, enlarged by a whole number and placed with `align` and `offset`. `fit: "cover"` (with a `size`) takes the smallest whole enlargement that covers the canvas and crops the overhang; `placement.visible` in the result is the `[x, y, width, height]` of the source that stays in view, so keep the action inside it. A video frame shows the pose active when the frame starts, so durations that are whole multiples of the frame time (33.333 ms at 30, 41.667 ms at 24) survive unchanged: prefer 100, 200 or 500 ms at 30 fps and 125 or 250 ms at 24 fps. Read `notes` for poses that changed length, poses shorter than a frame that are never shown, and whether the loop closes on the frame grid; `loops` can make it close. Author a scene at 192×108 or 240×135 to fill 1080p exactly; any other scene gets margins in its own background colour (when that is opaque), or fills the canvas with `fit: "cover"`. The result includes the ffmpeg command for an alpha `.mov`; Pixelbolt does not encode video. `sheet.scale` applies to every raster export and atlas coordinate. Metadata coordinates are already scaled; do not multiply them again. The browser player's optional `scale` is an additional display scale. Frames with anchors or points carry `anchor`, `pivot` and `points` in the atlas. `player.js` also exports `loadSpriteSheet(url)`, `frameAt(atlas, animation, ms)` and `drawFrame(context, sheet, name, x, y, { scale, flipX, anchor })` for games that draw many sprites into one canvas; `drawFrame` places a frame by its anchor and honors trimmed rectangles; `flipX` mirrors around the anchor corner, exactly as a compiled `mirror` pose does.

For grid-based game engines, prefer padding 0. For atlas importers, use the exact frame rectangles. Atlas animations list **expanded playback order** (including reverse/pingpong) and a loop flag.

At most 20,000 operations and 67,108,864 estimated drawing pixels are accepted. Animation exports across all sequences are also limited to 67,108,864 scaled pixels. CLI/MCP transport errors and render errors provide actionable paths; don't suppress them.

Large `pixel_render` previews are automatically sampled to stay inside inspection bounds; all animation frames are still exported. The response explicitly includes `preview.sampling` and a `playback` HTML path when rendering. Use `pixel_inspect` with a narrower selection for omitted detail. Contact sheets are static, even when arranged in playback order.
